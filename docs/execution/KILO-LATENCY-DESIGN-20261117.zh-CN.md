## 结论

有明确的本地优化空间，但目前没有生产分段数据，尚未确定实际延迟由排队、本地锁、连接建立还是上游生成主导。

推荐路径：**观测版本 → 正常流量定位 → 选择一至两个主要热点 → 优化版本**。第一阶段只补计时，不同时改变调度、锁或连接行为；第二阶段依据实际占比选改动，分锁与连接改造都不是预先必做项。

优先目标是降低高并发下的成功正文首字 P95，总耗时单独设定改善目标，同时约束吞吐、错误及取消。模型、推理档位、输出量、会话和出口规则保持不变。已采用的通过线为首正文 P95 降低至少20%、服务端总耗时 P95 降低至少10%；这些是工程验收目标，不是已经测得或承诺的收益。取得基线后、实施优化前冻结分组、窗口和比较规则；若可消除的本地成本不足以支撑目标，应先报告限制，由用户确认范围或目标调整，不在看到优化结果后放宽标准。

## 优化架构

### 请求路径与观测层

```text
客户端 → Caddy → CPA 业务Handler入口 t0
                  │
                  ├─ 请求解析与会话识别
                  ├─ 会话 gate／账号与出口准入 → 获得执行资格
                  ├─ 请求准备 → 发起上游请求 t_send
                  │               └─ 代理连接／上游响应头／上游生成
                  ├─ 识别首正文 t_text
                  ├─ 必要的归属持久化 → 协议转换与输出
                  └─ 正文写入并 Flush t_flush → 终态／取消 t_end
                       │
                       └─ Caddy → 客户端接收和显示（CPA 不掌握该时间）

请求级轻量观测：context 中的时间点、累计等待与计数
                       ↓ 请求结束时一次汇总
既有脱敏诊断出口 → 按并发和请求类型对比 → 选择优化模块
```

这是一条现有请求路径加一层轻量观测，不引入新代理服务、分布式追踪平台、数据库表或公网管理接口。观测层不参与选账号、重试、出口绑定与状态提交。

### 各层职责

| 层 | 负责什么 | 保持什么 |
| --- | --- | --- |
| HTTP入口与输出 | 记录到站、当前正文块实际 Flush 和请求结束 | Caddy 与现有 SSE 协议，不把首次任意 Flush 当首字 |
| 准入与出口 | 分别累计会话 gate、容量队列、选取锁等待；记录入队时负载和重选次数 | 账号与IP容量、公共/定向等待、已绑定账号归属 |
| Kilo执行器 | 记录出站、响应头及首次正文识别；与输出层共用请求关联 | 模型参数、设备profile、代理、NoReplay与工具协议 |
| 绑定存储 | 分别记录锁等待、读取与提交耗时 | 同文件原子性、先持久化再公开response/工具归属 |
| 请求汇总 | 输出一次脱敏性能记录，区分成功、失败和取消 | 不再发布一次用量，不重复计费；不逐token记日志 |

## 指标合同

所有内部计时使用单调时间。表中字段名是拟议诊断字段，不是已经上线的接口。

| 指标 | 拟议字段 | 严格口径 |
| --- | --- | --- |
| CPA首正文耗时 | `cpa_first_text_ms` | `t_flush - t0`；t0在Responses/Chat handler读取body之前，不含此前中间件及Caddy；CPA交付给下游，不等于客户端显示 |
| 上游首正文耗时 | `upstream_first_text_ms` | `t_text - t_send`；起点在实际出站调用前，包含连接等待，不全算模型计算 |
| 上游响应头耗时 | `upstream_headers_ms` | 出站到收到响应头；不是正文首字 |
| 准入等待 | `session_wait_ms`、`capacity_wait_ms`、`selection_lock_wait_ms` | 只记录对应等待边界；到站至获准的整体时间另标“准入前耗时” |
| 绑定开销 | `binding_lock_wait_ms`、`binding_read_ms`、`binding_commit_ms` | 归属维护的局部区间，可与其他区间重叠，不直接累加成端到端时间 |
| 首正文转发耗时 | `first_text_forward_ms` | `t_flush - t_text`；含这段期间的持久化、转换及下游背压，不直接归因为网络 |
| 服务端总耗时 | `server_total_ms` | `t_end - t0`；终态交付、失败或取消时结束，不替换旧执行器用量耗时 |

正文判定：只接受非空回答正文。reasoning、工具参数、created、心跳、完成与错误终态都不是正文。纯工具请求、正文前失败及取消的首正文指标为空，分别统计，不纳入成功正文 P95；已有正文后失败的请求也不混入成功分位数。

上游首正文的采样在正文识别后、归属持久化之前；下游采样须确认**当前写出的块**包含正文且 Flush 成功，不能仅凭“上游已经见到正文”标记任意后续 Flush。

现有监控的 Kilo TTFT只承接明确的上游首正文口径，不冒充CPA到站首字；细分指标先进入诊断摘要，不增加页面指标大屏或数据库字段。新记录未观测时通过可选字段表达缺失；历史0不回填，也不作为新性能基线。已有采集链路的毫秒精度与缺失语义须一并核验，不把实际小于1ms和未采集混为一类。其他通道的历史口径不改。

## 已排除的错误方向

- 正常 SSE 不是等整段回答结束才转发。`kilo_executor.go:599–655` 持续输出，`helps/kilo_protocol.go:142–204` 按完整 SSE 事件解析，`sdk/api/handlers/stream_forwarder.go:197–204` 写入后立即 Flush。
- 不是每次都新建 HTTP client。`helps/kilo_runtime.go:370–413` 已按账号、设备 profile、代理和路由模式缓存；缓存 client 不等于连接一定被复用。
- 同 session gate 在绑定提交后释放，并非整个回答期间锁住会话。
- 仓库 Caddy 示例不是生产配置。本轮未证明生产入口缓冲；不盲加 `flush_interval -1` 或扩大连接池。

## 分阶段实施

### 阶段一：只做观测版本

最小范围：CPA入口/输出挂点、准入等待、Kilo正文识别、绑定操作计时与Kilo有效TTFT传递。共用请求context，不重写业务执行链；必要的事件缺失态/展示调整只影响Kilo。

实现规则：

- 仅收集时间、计数、协议、负载及既有关联标识，不记录正文、密钥、授权token、代理凭据或新增身份指纹。
- 复用既有诊断输出控制，每请求最多一条汇总，不逐token输出、不新增独立同步文件写入。观测开销本身纳入本地对比。
- 公共输出仍走已验的错误脱敏；性能诊断属于内部材料，不增加对外响应字段。
- 现有usage发布时刻不移动，不增加第二次用量Publish。非Kilo通道、计费、工具续接与插件保持原行为。
- 首次实现不依赖特定传输库的HTTP追踪钩子。出站至首正文先作为整体测量；只有这个区间主导时才补连接内部细分。

此阶段交付“时间花在哪里”，不宣称已经加速。专项通过且获生产维护批准后，以正常流量形成观察样本，不做额外真实账号压测，不要求用户反复粘贴诊断命令。

### 阶段二：按主要耗时选择优化

从同类慢请求中的区间占比、等待计数及资源饱和情况判断，不把不同指标的P95直接相加。只选一至两个有证据的热点，避免调度、持久化和传输层同时变化。

| 测量发现 | 对应优化 | 核心保留条件 |
| --- | --- | --- |
| 代理池分组扫描占用明显 | 同次选择预计算group owner/active，把重复全表查询改为一次统计加查表 | 私有优先、顺序、同IP独占、容量与累计账号规则不变 |
| 不同caller相互阻塞明显 | 按既有caller文件路径分锁，同文件跨Store仍共享锁 | 原子提交、同步持久化和公开顺序不变 |
| 单Key多会话主要耗在同文件读写 | 分清全量解析/编码与Sync，再选择减少重复读取或变更提交次数 | 先确认外部写入约束，不默认上缓存、不直接取消Sync或重写存储 |
| 唤醒重选多、锁等待高 | 定向等待按账号唤醒，公共等待保留全池信号 | 保留generation顺序和不丢唤醒，不引入额外POST重放 |
| 后台出口协调占锁明显 | 减少无变化扫描，合并同轮允许合并的状态提交 | draining先提交、活跃租约与额度回收事实持久化 |
| 出站至首正文主导 | 先区分连接与上游等待；确认生命周期原因后再改善连接复用 | 设备/账号/代理隔离、及时取消与NoReplay；不为复用拖延终态 |
| 账号/出口已满而本地开销很小 | 把容量排队与上游时间明确呈现，再评估合规可用容量和负载分布 | 不把上调并发上限当默认修复，不借用绑定外账号 |
| 本地正文转发/Flush段主导 | 定位持久化、转换和下游背压各自占比，仅改实际阻塞点 | 不牺牲先落盘后公开，不用无限缓冲掩盖慢客户端 |

**同一客户端Key的请求仍属于同一个caller。** 跨caller分锁对单Key内部争用可能几乎没有收益，不把“多会话”误当成“多caller”。

降低本地等待通常同时影响首字和总耗时；若总耗时主要来自上游持续生成，本地首字改善不代表总耗时同比改善。保持输出语义、长度与推理档位后分别验收。

## 验收与发布

### 通过线：先固定标准，再看结果

主要性能组为正常业务中的目标高并发档，按到站时的负载归组，不根据请求完成快慢重新分类。P95明确指“成功且产生正文的请求”的95分位耗时；失败、取消、拒绝和纯工具请求分别计数，不填入0。

| 项目 | 已采用验收线 | 结论边界 |
| --- | --- | --- |
| 高并发CPA首正文P95 | 候选不高于基线的80%，且改善超出同条件样本波动 | 达到后可判首字子目标通过 |
| 同组服务端总耗时P95 | 候选不高于基线的90%，且改善超出同条件样本波动 | 达到后可判总耗时子目标通过；持平不叫总耗时优化完成 |
| 低并发首字与总耗时 | 不出现超过基线5%且超出样本波动的退化 | 避免高并发改善以日常使用变慢为代价 |
| 成功吞吐 | 在请求到达负载相当且需求充分时，不出现超过5%且超出样本波动的下降 | 流量不足时不推断吞吐提升或退化 |
| 成功率、拒绝率、取消率 | 各自不出现超出预先确定的基线波动范围的恶化；分母为全部相应业务请求 | 不允许通过让慢请求失败、取消或退出统计来改善首字 |
| 业务正确性 | 不新增由改动导致的丢请求、重复模型请求、重复用量、归属错配或续接失败 | 任一成立均阻止候选放行 |

同时给出“在固定首字目标时间内成功产生正文的请求数／全部适用请求数”。适用请求按请求类型预先确定；纯工具请求分组，失败或取消的正文类请求仍保留在分母中。该指标用于揭示只统计成功样本产生的偏差。

基线为观测版本的正常流量，不采用旧的未采集TTFT或无分段数据。优化前后固定模型、推理档位、上下文和输出量分组、有效账号/出口容量、并发档及比较窗口；记录实际到达率与排队负载，禁止降低并发或缩短输出后声称提速。

目标高并发组前后各至少200条成功正文记录，同时报告全请求数和各结果数量。200条只是起始下限，不自动证明P95稳定。采样窗口、窗口内分段方式及不确定性计算口径在实施前确定；使用相同条件的分段样本检查变化是否超出自然波动，样本不足或区间重叠导致结论不清时标记“待验收”，不补跑无关测试或无限追加观察窗口。

### 验收结论分类

- **观测完成**：能可靠解释耗时分布，但尚无优化效果结论。
- **首字子目标通过**：首字达到通过线且正确性与非退化条件满足；总耗时未达到改善线时明确说明。
- **服务端性能验收通过**：首字与总耗时两个子目标及所有保护条件均通过。
- **客户端体验已验证**：同一客户端正常使用有独立的发送、首正文接收和结束记录支持；显示时间若没有客户端测量就不作结论。仅CPA改善、客户端未采集时只报告服务端通过；若客户端仍无改善，继续定位CPA以外的路径，不宣告用户体验问题已解决。
- **待验收／未通过**：证据不足为待验收；目标未达到或发生回归为未通过。构建、测试、健康检查或退出码0都不替代性能验收。

| 优化专项 | 所选瓶颈开销下降，分别核对首字和总耗时通过线，并满足低并发、吞吐和业务结果约束 | 未达到则报告具体未通过项；有退化在候选内调整或撤回，不顺手加入新优化线 |
| 业务兼容 | 归属持久化、会话/设备/出口、工具续接、NoReplay与错误脱敏保持既有合同 | 阻止该候选发布，保留原稳定版本 |

本地正确性测试使用可控事件/假时钟验证顺序；性能比较使用真实单调时间，固定场景、并发档和样本量，覆盖单Key多会话与多Key并发。复用未变化的既有验收证据，只补改动相关专项，不重复全套历史门禁。
