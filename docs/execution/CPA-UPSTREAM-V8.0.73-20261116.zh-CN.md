## 优先保护的接缝

| 接缝 | 需要保持的本站行为 | 验证目的 |
| --- | --- | --- |
| Executor 注册、包装及热更新 | 正式 Kilo 执行器、BPS 宿主实例绑定与最终通道判断一致；避免重复包装或漏注册 | 捕获升级后模型可见但实际执行拒绝、错走通道等回归 |
| 管理凭据上传、更新、删除 | 稳定凭据身份、provider、插件归属及额度关联引用保持一致 | 捕获导入后身份变化、错误删除或关联失效 |
| AuthManager 调度与错误处理 | 通道隔离、不重放、账号与出口槽位释放、已确认的等待预算和续轮归属 | 捕获共享 SDK 变化造成的调度与资源回归 |
| Responses / Chat / WebSocket | 维持工具调用 ID、历史、图片与失败终态；流式和取消语义正确 | 捕获协议适配及共享处理器变化影响本站请求链 |
| 构建与发布清单 | 新增上游文件和依赖进入实际交付产物；现有三角色发行结构有效 | 捕获本地源码完整但 CI 打包漏文件、插件装载不兼容 |

验证必须走实际交付组件、本地模拟上游和隔离运行条件，不用测试 Executor 替代正式 Kilo Executor，也不以权限函数单测代替 BPS 宿主真实分发。首次调查不跑测试；实施后依据最终 diff 决定需要重跑的专项，引用仍对应同一代码输入的历史证据。共享调度文件改变时，相关 NoReplay、释放与续轮专项属于受影响验证，而非无意义重复。

### 已查实的最小整合选择

1. **Executor wrapper：** 上游增加统一注册包装及 ownership/revision 管理，默认空 hook 保留原对象。本站 Kilo 零账号管理、配置更新和代理池管理存在具体类型与附加能力访问；本次保留 Kilo 原执行器分支，不为内核升级引入通用包装改造。BPS 插件注册边界、可信 `ExecutionChannel` 与最终 adapter 判定保持原样。专项验证重注册、外部替换和共享 session 生命周期，并验证 Kilo 仍使用同一池。
2. **v8 凭据多身份：** 接入上游多身份解析和按源文件 reconciliation，但 Kilo 写前保护须位于 v8/v0 分流前，解析所得身份在落盘前保留适用的 BPS replacement 判定。保留 multipart Kilo 批量预检；上传、覆盖、删除之后，Manager、模型注册与 watcher 的身份要一致。额度引用和 continuation 保留真实 AuthID：同身份刷新继续有效，删除或换身份按既有状态失败，不漂移绑定。文件原子替换不等于整条上传链具备事务回滚。
3. **依赖：** Go 仍为 `1.26.10`；moego 升到 `v0.1.0-alpha.3` 并移除旧 replace，需要编译和插件接线专项。bbolt 仍为 `v1.5.0`，仅由间接依赖改为直接依赖，不据此推定要迁移数据库。上游 refresh journal 涉及的持久化后端，实施时只核本站实际启用路径的兼容和回退影响。
4. **来源合同：** `deploy/production-wiring.contract.json.source_files` 当前有 4614 项；现有打包器按候选 Git tree 全等核对。新增的 97 个上游路径及其余变化必须进入新候选的准确映射，未更新会被拒绝打包，而非静默漏包。按最终候选更新映射及受影响接线证据，不复制旧 PASS，也不另建发布框架。

已有专项路径与建议命令见 A 的 `UPSTREAM-UPGRADE-FACTS.zh-CN.md` 及 S 的 `UPGRADE-SEAMS.zh-CN.md`。实施时按最终 diff 收敛执行集合；新增交叉验证只补 Kilo 单池与 wrapper 生命周期、v8 多身份与本站写前保护两组。命令没有匹配测试、跳过或失败均不计通过；涉及并发锁的实际增量才追加对应 race 验证。

## 服务器操作

沿用已完成的 GitHub 构建与固定版本一键更新工具，不重走首次 Kilo 迁入时逐段传包、prepare、apply、start 的人工流程。更新入口自动串联既有前检、停态备份、切换、内网健康和恢复本轮原入口。

现场尚需一次接入：依据已核站点资料落位 `mx-update` 及私有站点登记，确认实际无凭据健康 URL / 预期状态和目标路径占用。这是站点接入，不是升级内核；已有 rc.2 的 GitHub 构建成功也不表示服务器已安装该入口。

接入完成且新版本已发布后，日常命令形态如下；其中版本必须是包含新内核的 **MX-CPAMP 本站版本**，不是上游 `v8.0.73`：

```sh
/opt/cpa-stack/bin/mx-update.sh --site /opt/cpa-stack/site.json --version <本站固定版本>
```

一次 `UPDATE` 确认包含本轮正常维护与健康后恢复原入口。停服前失败不停止原服务；维护开始后失败保留现场并按既有逻辑停止入口和应用，随后依据回执定向恢复，不自动回灌数据库或循环重跑。

真实更新前确认维护窗口和回退版本，保留既有持久状态和备份。若实际整合引入持久化格式或数据库动作，必须单列兼容与回退影响；调查尚未形成这种变更的放行结论。业务失败与入口健康分别记录，页面可打开不替代真实模型验收。本轮不调用真实账号、模型或付费探测，不改线上数据库。

## 后续自动发现与一键更新建议

本节为建议，尚未实施，也未开启任何定时任务。用户目标是发现新版后方便升级；实际安装对象仍是完成适配的本站发行，不是官方裸内核。

### 两级版本来源与页面状态

- 官方来源回答“CPA 是否有新版”，本站发行来源回答“是否已有兼容本站、资产齐全且已验的可安装版”。正式通道不自动选 draft、预发布或不支持的平台产物。
- 复用现有设置页面，紧凑显示当前本站版本、内含 CPA 版本、官方版本、可安装本站版本及检查时间，不新增主导航。来源请求失败显示“检查失败”并保留上次观测，不冒充“已是最新”。
- 官方领先而本站尚未适配时显示“上游有新版，待适配”；本站已验发行包含新内核时显示“可更新”；完成现场更新和健康收尾后才更新“当前运行版本”。
- 首期在打开更新区域时按缓存有效期检查，并提供手动“检查更新”；既有不创建定时任务的边界保持。未来若要无人值守发现，再单独确定触发方式，不静默启动计划任务。

### 发布侧与安装侧分开

发布资产增加明确的 CPA 上游版本和提交信息，并绑定本站版本、本站提交与现有镜像清单。检测服务只读这些公开版本元数据，不读取用户账号或推理凭据。

后续可自动生成上游差异清单和隔离整合候选，复用 GitHub Actions 做受影响验证。干净合并不等于 Kilo/BPS 兼容：冲突、测试失败或缺少关键接缝证据时保持“待适配”，不自动合 main 或冒充正式发行。通过既有审查发布后，客户端才获得可安装版本。首期先落实检测与固定版更新，不把无人值守源码整合列为一键安装的前置工程。

### 一次操作的执行边界

现有 `mx-update` 是宿主机命令行入口，接受固定版本并通过交互确认进入维护；管理页面直接更新尚待开发。已确定的交付是“网页选择固定本站版本、确认一次维护影响后直接执行”，不是生成命令供用户复制。保留命令行作为恢复入口。

网页“立即更新”补充受限本机 Unix socket 与按需 systemd 任务：管理权限确认固定目标版本和维护影响后，仅启动既有 updater 的独立更新任务。任务不依赖即将被重启的 Manager 进程存活，状态写入既有轮次记录；页面恢复后读取同一任务结果。接口只接收本站已验版本，不接受任意命令、下载地址或文件路径，不把 Docker socket 交给页面服务。客户端推理 Key 不获得该权限。首次安装另行授权，本轮仅确定方案。

执行时沿用站点锁和既有下载、校验、备份、切换、健康及入口恢复逻辑；与商店直接安装、ZIP 安装及后续异步 reload/必要重启共享同一后端互斥，持续到实际终态。并发点击关联已有更新任务，不启动多次维护。健康未通过时保持既有失败保全逻辑，不自动回灌数据库，不显示升级成功。首次站点登记仍须完成一次，后续不重复询问已保存的路径、Compose 链及健康地址。
